# Efficient Text-to-SQL — Part 3

CS-GY 6083 Principles of Database Systems, Fall 2026 · Shreyansh Saurabh (ss21034)

A web application and experiment pipeline that turns English questions into PostgreSQL
queries with Claude, then uses PostgreSQL's `EXPLAIN ANALYZE` plan to ask for a **faster
query with the same result**. Every attempt, plan, timing and LLM call is logged in the
Part 2 schema (`t2s`), so accuracy (BIRD execution accuracy), speed (BIRD R-VES) and cost
can be compared between the baseline pipeline (write + fix) and the plan-guided pipeline
(write + fix + rewrite).

Part 3 replaces Part 2's simulated rows with the real BIRD Mini-Dev questions and databases,
and real runs.

## Requirements

- PostgreSQL 14+ (`psql` on the PATH; tested on 14.20, Homebrew)
- Python 3.12
- An Anthropic API key. The pipeline calls `claude-haiku-5-5` by default ($0.10 / $0.50 per
  million tokens): the full experiment (196 questions × 2 configs × 3 repeats) costs well under $1.
  A hard cap (`T2S_BUDGET_USD`, default $3) stops all LLM calls once logged spend reaches it.
- About 3 GB free disk: BIRD Mini-Dev zip (0.8 GB) + loaded tables (~1.5 GB)

## Setup

```bash
cd part3
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env                 # then set ANTHROPIC_API_KEY and SECRET_KEY

# BIRD Mini-Dev (CC BY-SA 4.0): official zip with the PostgreSQL dump and questions
mkdir -p data && curl -L -o data/minidev.zip https://bird-bench.oss-cn-beijing.aliyuncs.com/minidev.zip

# Rebuild everything: results DB (text2sql) + target DB (bird), questions, gold timings
.venv/bin/python scripts/load_bird.py --zip data/minidev.zip

# Trusted setup: researcher account (researchers cannot self-register)
.venv/bin/python scripts/create_user.py --email you@nyu.edu --name "Your Name" --role researcher

# Web app on http://127.0.0.1:5050
.venv/bin/python -m webapp.app
```

`load_bird.py` is the reproducible rebuild: it drops and recreates schema `t2s`, applies
`sql/01_schema.sql` (Part 2, unchanged) and `sql/02_part3_migration.sql`, streams the
Mini-Dev PostgreSQL dump out of the zip (no 1 GB extract), keeps only the five databases
used here, gives each its own schema in database `bird`, and measures every gold query.
Pass `--skip-dump` to rebuild only the results database.

## Running the experiment

```bash
# small pilot first (10 questions x 2 configs)
.venv/bin/python scripts/run_experiment.py --experiment pilot --limit 10
# full run: 196 questions x {baseline, plan_guided}; resumable if interrupted
.venv/bin/python scripts/run_experiment.py --experiment main-v1 --repeats 3 \
    --description "196 Mini-Dev questions, baseline vs plan_guided" --freeze
# tables for the report
.venv/bin/python scripts/eval_report.py --experiment main-v1 > docs/evaluation_results.md
# JSON files behind the online results dashboard
.venv/bin/python scripts/export_dashboard.py --experiment main-v1 --out data/dashboard
```

Researchers follow progress and read each experiment's report in the web app at `/experiments`.

## Schema changes since Part 2 (migrations)

All in `sql/02_part3_migration.sql`; Part 2's `01_schema.sql` is unchanged.

| # | Change | Why |
|---|---|---|
| M1 | `app_user` table (email unique, scrypt hash, role `analyst`/`researcher`) | web login and roles |
| M2 | `target_database.pg_schema`, `target_database.schema_prompt` | where each BIRD DB lives; the frozen schema text the LLM sees |
| M3 | `question.source` (`bird`/`user`), `created_by`, `created_at`; `gold_sql` and `difficulty` nullable **only** for `source='user'` (CHECK); sequence `user_question_seq` from 1,000,000 | users can ask their own questions, which have no gold SQL |
| M4 | `run.user_id` (ON DELETE SET NULL), `run.finished_at`, `run.error_detail` | who launched a run; run duration; pipeline-level failures (API errors) |
| M5 | `experiment.description` | |
| M5a | `pipeline_config.effort`; unique-settings key now includes it | current Claude models reject `temperature`, so it is stored as 0 and not sent; effort is the real setting |
| M5b | `generated_query.accepted`, `reject_reason` with CHECKs | an accepted rewrite can be superseded later, so `is_final` alone cannot tell accepted from rejected |
| M6 | the Part 2 indexes + `run(user_id, started_at)` | used by the queries and the app |
| M7 | views `v_run_rves` (R-VES reward per run), `v_rewrite_outcome` (each rewrite vs its base query) | reports |

Test data is regenerated by the loader (real BIRD questions, gold timings) and by real runs;
Part 2's simulated rows are not used.

## Security measures

- Passwords: Werkzeug `generate_password_hash` (scrypt); never stored or logged in plain text.
- Sessions: Flask signed cookie holding only `user_id` (HttpOnly, SameSite=Lax); the user and
  role are re-read from `app_user` on every request; logout clears the session.
- Authorization is checked on the server for every route (`login_required`,
  `researcher_required`, run visibility rule); hiding links is only a convenience.
- CSRF token on every POST form.
- All SQL uses psycopg bound parameters; free text is length-checked and validated.
- Jinja2 autoescaping for everything users or the LLM wrote (questions, names, SQL, errors).
- LLM-written SQL runs in a `READ ONLY` transaction, as role `llm_reader` (SELECT on the BIRD
  schemas only), with a 30 s `statement_timeout`, via the extended protocol (one statement
  only), and is always rolled back. It cannot reach the results database at all.
- Analysts can have at most 3 runs in progress, and a project-wide spend cap (`t2s/costs.py`)
  is checked before every LLM call; the web app refuses new runs once it is reached.
